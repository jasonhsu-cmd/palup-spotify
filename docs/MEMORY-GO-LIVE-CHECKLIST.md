# Cross-visit memory — go-live checklist

> **Status: NOT READY. Several conditions below are unmet.** This document is the single gate list for
> flipping `MEMORY_ADR_ACCEPTED` (`packages/widget-memory/src/flag.ts`) and moving ADR-0015 from
> *Proposed* to *Accepted*. That flip is **human-only** (CLAUDE.md §3, ADR-0015 Status): it requires a
> named human owner, a recorded `security-reviewer` sign-off, and a recorded **legal** sign-off. No build
> agent may perform it, and no amount of green CI substitutes for the legal conditions.

**What the flip actually does.** `isMemoryEnabled()` is `MEMORY_ENABLED === "true" && MEMORY_ADR_ACCEPTED`.
Both must be true. The env var alone can never enable memory (NN#1) — the const is a build-time change that
goes through code review. Until then the entire subsystem is inert: no fact is written, none is recalled,
and production behaviour is byte-identical to before the program.

**How to read this list.** Every item is either **MET** (with the evidence), **OPEN** (with what is
missing), or **ACCEPT** (a residual risk that must be consciously signed off rather than fixed). An item
being "in a PR" is *not* met — merged and verified is met.

An operator cannot reconstruct that a second subject's consent record drove a given refusal. **Not closed this round** — N2's write-through DOES add a NEW, adjacent audit trail for the specific case where the merge discovers a durable-worthy `"out"` (a `consent.record` entry is written the first time), so an operator inspecting the log can see *that* the account's consent state changed, but that entry does not itself say "because a guest row was consulted" nor identify which guest row. Extending `service.ts`'s own `write.*`/`write.refused` audits to carry a PII-free "a guest row was consulted, merged tiers X/Y" marker (per N4's own text) would need a new `MemoryCtx` field threaded through `remember()` and a change to the pre-existing, tested "consent-denial is silent" invariant (`chat-memory-remember.test.ts`) — a larger, separately-scoped change, not made here to avoid touching that locked-in behavior without its own solution-architect review. | Bounded: the decision itself is still correct and fail-safe (a stranger's row can only make the caller's own write MORE restrictive) — what is missing is reconstructability, not correctness. **Not self-limiting:** an earlier draft said this was self-limiting after N2, inheriting the C8 "one-shot" claim that has since been struck as false. |
| C10 | **NEW (PR #152 round 3) — a third party can DURABLY deny a victim's memory by poisoning their consent.** `/widget/token` mints a tenant token from a *publishable* embed key with no auth, so an attacker holding a victim's guest `anonId` can `POST /consent` recording `"out"` for that subject (this half is pre-existing C1). What round 3's write-through (N2) adds: on the victim's next signed-in `/chat` turn — while their browser still presents that `anonId` — the merge **persists `"out"` onto `acct:<victim>`**. Before N2 this was per-turn and self-healing; it is now durable against new devices, cleared storage, and the victim's own later opt-in. | Direction is privacy-CONSERVATIVE (it can only deny memory, never grant it), which is why it is accepted rather than fixed — but it is a genuine third-party-triggered durable denial and must be signed knowingly. Distinct from C7 (the shopper's own stale record) and C8 (a caller poisoning their own account).  Also note: unlike the other two memory writes on `/chat`, the write-through does NOT carry `!no_autonomous_action`, so a poisoned `"out"` can be durably persisted even on a guardrail-halted turn. Deliberate — the write is strictly restrictive, so suppressing it would only DELAY honoring an opt-out — but recorded here rather than living only in a code comment. The kill switch still overrides it (NN#4, test-locked).  Attribution caveat: a `/consent` call carrying NO shopper token still records `actor: "shopper"` / `source: "shopper"` for a subject the server verified nothing about (this bearer path), so the immutable log cannot distinguish a verified shopper's own choice from a bearer-capability write. |
| C11 | **NEW (PR #152 round 3) — consent records survive `/forget`, and one of them is now created autonomously.** `eraseSubject` (`widget-memory/src/erasure.ts`) deletes the subject's vector namespace and audits it; it never touches the `memory_consent` KV. So after a signed-in shopper's "forget everything", both their guest row and the `acct:` row written by N2's merge remain. No surface removes them, and nothing in `docs/` previously recorded this erasure-scope decision. | Retaining an `"out"` is defensible as a SUPPRESSION record (it is what keeps a withdrawal effective after erasure). Retaining an `"in"` after an erasure request is NOT obviously defensible and needs a decision. Newly acute because N2 means the `acct:` row was never created by the shopper at all. Requires a stated decision at go-live, not necessarily a code change.  **B12 adds a second such collection:** the `guest_account_link` record (a browser-id ↔ account association) is written with no TTL. **UPDATED (C15(b)):** `/forget` now DOES touch it — `clearGuestLinkIfOwnedBy` removes the record — but ONLY when the presented anonId's link already points at the CALLER's own verified account; `/forget` from any other account still leaves it standing (see C15). So the "untouched by `/forget`" claim above is no longer general: it is untouched for every account except the one it is already linked to. |
| C12 | **The consent write-through's failure is not in the immutable audit log.** If `recordConsent` throws on the `/chat` path, `server.ts` catches and emits a PII-free console signal (`tenant` + error CLASS only, matching `retention.ts`'s rule) — but NO audit entry, and unlike the retention sweep's signals it omits the hashed `subjectRef` and attempted count, so an operator sees THAT a write-through failed, not for WHICH subject. The turn itself still honors the merged `"out"` (the read-time merge already applied it), so the failure degrades to pre-N2 per-turn behavior, never to a permissive one. (An earlier draft of this row said "no audit entry, no operator signal" and contrasted it with the sweep — both wrong: the console signal exists and uses the same mechanism. Overstating a residual is still misdescribing the code.) | Safe direction, but a persistent store failure would silently mean opt-outs never become durable, identifiable only at the tenant level. |
| C13 | **Two independent shopper-principal derivations.** `/chat` derives the verified shopper inline (`server.ts`) rather than calling `verifiedShopperIdFor`, which `/consent` and `/forget` use. Both apply identical gates today (feature flag, verified merchant principal, `kind === "shopper"` AND the explicit `verified` flag, cross-shop tenant check) and reviewers confirmed equivalence — but it is two implementations of one security decision. | Narrow drift risk, documented in `server.ts` but previously absent from §C, so a signer accepting the residual list never saw it. Unifying them is a follow-up, not a blocker. |

> **RESOLVED (human owner) — C15 link squatting: option (b), as built.** Both reviewers had blocked on
> this, agreeing it must be resolved by design, not wording, across three options: **(a)** ship the link
> with C15 as an accepted residual (deny-only, 128-bit precondition, rate-limited, kill-guarded); **(b)**
> make the link revocable and self-healing; **(c)** drop the link, leaving C14 open and disclosed. The
> human owner chose **(b)**. As built (see the C15 row above): a verified account owner may overwrite the
> link at any time (last-VERIFIED-writer-wins, atomic compare-and-write) and may clear it via `/forget`.
> **One clause of the original (b) sketch was deliberately NOT built**: "the effect applies only where the
> guest row is absent or agrees" — layering that scoping ON TOP of revocability would re-open C14 for a
> shopper whose guest row explicitly says `"in"` while their account says `"out"`, undoing B12's own
> remedy. Revocability alone is the fix that was needed; effect-scoping was assessed as the fallback for
> if revocability had been impossible, not an addition to it.
> The underlying blocker is the same one that killed B12's fact migration: **nothing in this system proves
> an `anonId` belongs to the caller.** Until that primitive exists, every control keyed on a client-supplied
> `anonId` inherits this class — including this fix: an attacker who keeps re-obtaining the same anonId can
> keep re-squatting. See the C15 row's own residual column for the precise, non-overclaimed statement.
