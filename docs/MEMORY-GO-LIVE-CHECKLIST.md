# Cross-visit memory — go-live checklist

> **Status: NOT READY. Several conditions below are unmet.** This document is the single gate list for
> flipping `MEMORY_ADR_ACCEPTED` (`packages/widget-memory/src/flag.ts`) and moving ADR-0015 from
> *Proposed* to *Accepted*. That flip is **human-only** (CLAUDE.md §3, ADR-0015 Status): it requires a
> named human owner, a recorded `security-reviewer` sign-off, and a recorded **legal** sign-off. No build
> agent may perform it, and no amount of green CI substitutes for the legal conditions.

**What the flip actually does.** `isMemoryEnabled()` is `MEMORY_ENABLED === "true" && MEMORY_ADR_ACCEPTED`.
Both must be true. The env var alone can never enable memory (NN#1) — the const is a build-time change that
goes through code review. Until then the entire subsystem is inert: no fact is written, none is recalled,
and production behaviour is byte-identical to before the program.

**How to read this list.** Every item is either **MET** (with the evidence), **OPEN** (with what is
missing), or **ACCEPT** (a residual risk that must be consciously signed off rather than fixed). An item
being "in a PR" is *not* met — merged and verified is met.

## C. Residual risks to ACCEPT explicitly

These are known, bounded, and not planned to be fixed before go-live. The named owner must accept them in
writing — silence is not acceptance.

| # | Residual | Why it is bounded |
|---|---|---|
| C1 | **`anonId` is a bearer capability — for ANONYMOUS GUESTS ONLY (narrowed), and only for data written AFTER sign-in with the principal actually sent.** Read literally, not as a general closure: **closed for data written after sign-in, once the client sends the principal** — `x-shopper-token`, now sent on `/chat`, `/consent`, AND `/forget` alike (PR #152 fixed the latter two, which the shipped widget previously omitted it from). Two things this does **not** close: (i) neither `/consent` nor `/forget` actually *requires* the shopper token — an attacker simply omits it and the request falls back to the unauthenticated `anonId` path exactly as before, for **any** caller, well-formed guest id in hand; (ii) guest-era facts are never migrated into the account (B12), so a shopper with guest history stays fully bearer-exposed on that guest-era data even after signing in. | 128-bit CSPRNG (not enumerable), per-tenant, rate-limited, kill-guarded. Blast radius is the victim's own preferences; this **does** include read access — `/chat` recall queries the victim's namespace and can surface their fact text into the model's reply for whoever holds their `anonId` (pre-existing behavior, not introduced or changed by this PR — the prior "no read access" claim here was false before this PR too). No cross-tenant reach; orders/account untouched. |
| C2 | **Subject-scoped auth — closed end-to-end for a verified shopper's OWN `/chat`, `/consent`, and `/forget` calls, as of PR #152.** Widget auth binds the *tenant*; the shopper subject is additionally bound to the verified `x-shopper-token` principal (`memorySubjectId`, `identity.ts`), gated on the explicit `verified` flag and the cross-shop tenant check, on all three surfaces — the shipped widget now sends that header on all three (previously `/consent`/`/forget` did not: a signed-in shopper's own consent/erasure calls looked anonymous to the server, so `/forget` returned `{ok:true}` while erasing nothing — PR #152 BLOCK-2). A guest-recorded opt-out is additionally honored at sign-in by a **per-request, read-time** restrictive merge (PR #152 BLOCK-1, `mergeAccountConsent`) — note this does NOT write anything into the account record and the consent record does NOT follow the subject: the merge only fires on a turn where the client still presents the same validated guest `anonId`. So sign-in can STILL silently re-permit a write the shopper opted out of whenever that id is absent — a fresh browser, cleared storage, or after the widget's own `forgetMe()` mints a new `anonId`. Durability requires the consent migration in B12. Guests remain principal-less by construction. | Closed for an authenticated shopper's own calls; the residuals are exactly C1's guest-bearer-capability case and B12's un-migrated guest-era facts, not separate risks introduced here. |
| C6 | **RESOLVED — PR #152 round 3 (N1).** Previously: a signed-in shopper's "forget everything" did NOT erase their guest-era facts, while the UI reported success — `/forget` targeted `acct:<shopperId>` only and ignored any supplied `anonId`. **Fix landed:** `/forget` now ALSO erases a validated `anonId` presented alongside the shopper token (the shipped widget's own `forgetMe()` already sends both — `index.html`'s `prevAnonId`), so both namespaces end up empty and the UI's "Done — I've cleared what I remembered" is true whenever the client presents both. Proven by execution: `forget.test.ts`'s new N1 test (red without the fix, green with it). This is safe by the SAME reasoning C1 already accepts: the guest path a few lines above already lets an *unauthenticated* caller erase any `anonId` they hold, so doing the same erase on a verified turn grants an attacker nothing new — see the (intentionally reversed) "THE ATTACK: POST /forget" test in `subject-scoped-memory-auth.test.ts`. **Residual, moved to B4:** the erasure is only as good as the client presenting that `anonId` — it is on-demand (via `/forget`), not proactive; the *opportunistic per-turn TTL sweep* on `/chat` still does NOT visit a signed-in shopper's guest-era namespace (attempting that regressed the protected F1 recall test — see B4). A shopper who never calls "forget everything" and whose guest-era facts simply expire will not have them physically reclaimed until B12's migration or a future scheduled sweep job exists. | N/A — resolved; see B4 for the remaining opportunistic-sweep residual. |
| C7 | **A stale guest opt-out defeats that same shopper's later, authenticated opt-IN.** Guest records `"out"`, shopper signs in and explicitly grants consent against `acct:<id>` — the read-time merge still resolves `"out"`, so no writes occur, while the manage panel (local state) shows memory as on. **Round-3 update (N2) — restated, NOT fixed, made STICKIER by design:** N2 durabilizes the merge's restrictive output (see B12), and "out always wins outright" (`mergeConsentTier`) is what makes a guest opt-out survive sign-in at all (the whole point of N2). The same rule now means a stale guest `"out"` can durably OVERWRITE the account's fresh, explicit `"in"` the next time the client presents that guest `anonId` — proven by `consent-restrictive-merge.test.ts`'s new "C7 (restated)" test: after the shopper's explicit `/consent` opt back IN, a turn re-presenting the stale guest `anonId` re-durabilizes `"out"`, and — unlike pre-N2 — a SUBSEQUENT turn presenting NO guest `anonId` at all now ALSO stays denied (previously, omitting the id would have let the account's fresh `"in"` govern again). This is the accepted cost of N2's write-through, not an oversight; N2 was scoped (per its own requirement) to write through ONLY the restrictive direction. | Still fails in the privacy-safe direction (never silently re-permits a write); the residual has shifted from "per-turn, easily self-resolved by omitting the anonId" to "durable until the stale guest record itself is cleared." No shopper-visible way to clear the stale guest record today; resolved by the same B12 migration (which would retire the guest record entirely on merge). |
| C3 | **`query` is a brute-force namespace scan, not ANN.** | Embeddings were dropped in scope (FAST-V1); the only consumer uses the empty-text list-all idiom. Documented in-adapter. |
| C4 | **Free-text willingness-to-pay is prompt-governed, not structural.** The *disposition* WTP path is structurally blocked (no `inferred` provenance); a WTP claim inside free-text fact content is caught by the distiller prompt + eval, not a classifier. | Contained today by the read-time consent gate; confirm the distiller eval covers it. |
| C5 | **Merchant per-store disable toggle and the Invariant-11 sensitivity-policy authorship/review process** are ADR-0015 open items, not built. | Tenant policy may only *narrow* what is remembered; absence means the conservative default applies. |
| C8 | **NEW (PR #152 round 3, N3) — cross-subject consent oracle / denial primitive.** `/chat`'s restrictive-merge lookup (`server.ts`, feeding `mergeAccountConsent`) does a `lookupConsent` against a **caller-supplied** `anonId` (any signed-in shopper's own turn, as long as they attach a well-formed `anonId`) and lets that stranger's row govern the caller's OWN write this turn. A caller who wants to learn a target's `memoryOrdinary` tier can attach the target's `anonId` and observe whether their own write went through: refused ⇒ the target's row says `"out"`; succeeded ⇒ it does not. This is a 1-bit read of another subject's consent state plus a memory-denial primitive, newly reachable from an AUTHENTICATED turn rather than the anonymous C1 bearer-capability path. | Blast radius is bounded — holding a 128-bit `anonId` already grants the larger C1 read (recall queries + serves the target's own fact text), so this adds a narrower, indirect 1-bit signal on top of an already-larger exposure, not a new class of access. **N2's write-through changes its shape, not its existence:** the FIRST time a caller's own turn discovers a target's `"out"`, N2 durably writes that `"out"` onto the CALLER'S OWN account record (see B12/C7). Every subsequent turn is then refused regardless of what target is attached (the caller's own account is now durably `"out"`), so the oracle degrades from "repeatable, one query per target" to effectively **one usable probe per attacker account** — after the first target found to be `"out"`, further probes reveal nothing (the caller's own write is refused unconditionally from then on, whether or not the newly-probed target is actually `"out"` too). Not closed; documented here as the newly-required residual row. |
| C9 | **NEW (PR #152 round 3, N4) — the cross-subject consent read (C8) is unaudited.** When subject X's write is refused because subject Y's row said `"out"`, nothing in the immutable log attributes the decision to a second subject's record: `lookupConsent` writes no audit of its own, and `service.ts`'s `remember()` writes NO audit at all for a plain consent-gate refusal (`write.refused` is emitted only for the SEPARATE encryption-fail-closed case — `chat-memory-remember.test.ts` locks this in deliberately). An operator cannot reconstruct that a second subject's consent record drove a given refusal. **Not closed this round** — N2's write-through DOES add a NEW, adjacent audit trail for the specific case where the merge discovers a durable-worthy `"out"` (a `consent.record` entry is written the first time), so an operator inspecting the log can see *that* the account's consent state changed, but that entry does not itself say "because a guest row was consulted" nor identify which guest row. Extending `service.ts`'s own `write.*`/`write.refused` audits to carry a PII-free "a guest row was consulted, merged tiers X/Y" marker (per N4's own text) would need a new `MemoryCtx` field threaded through `remember()` and a change to the pre-existing, tested "consent-denial is silent" invariant (`chat-memory-remember.test.ts`) — a larger, separately-scoped change, not made here to avoid touching that locked-in behavior without its own solution-architect review. | Bounded by the same C8 reasoning: the underlying read is already narrow and self-limiting after N2. The audit gap is a forensic/observability gap, not an additional access grant — an operator who suspects abuse can still correlate `consent.record` timing with a specific shopper's account, just not automatically. |

## D. The flip itself (human, in order)

1. Confirm every **A** item is closed and recorded in ADR-0015 — not merely done, but *written down*.
2. Confirm every **B** item is MET and verified against the deployed configuration.
3. Sign off the **C** residuals explicitly, by name.
4. Set ADR-0015 Status → **Accepted**, recording owner + security + legal sign-offs.
5. Flip `MEMORY_ADR_ACCEPTED` to `true` (`packages/widget-memory/src/flag.ts`).
6. Set `MEMORY_ENABLED=true` and `WIDGET_AUTH_REQUIRED=true` in the target environment, with the
   encryption key provisioned.
7. Ship progressively (canary → full) per CLAUDE.md §3.2, watching the audit log and the kill switch.
   **Prod is never auto-deployed.**

**Rollback:** the kill switch halts memory writes immediately at any scope. Reverting the flag const
returns the system to fully inert. Neither undoes data already written — erasure (`/forget`, `erase.subject`)
is the data-removal path, so verify B5/B6 *before* the first real write, not after.
