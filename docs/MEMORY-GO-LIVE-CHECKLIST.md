# Cross-visit memory — go-live checklist

> **Status: NOT READY. Several conditions below are unmet.** This document is the single gate list for
> flipping `MEMORY_ADR_ACCEPTED` (`packages/widget-memory/src/flag.ts`) and moving ADR-0015 from
> *Proposed* to *Accepted*. That flip is **human-only** (CLAUDE.md §3, ADR-0015 Status): it requires a
> named human owner, a recorded `security-reviewer` sign-off, and a recorded **legal** sign-off. No build
> agent may perform it, and no amount of green CI substitutes for the legal conditions.

**What the flip actually does.** `isMemoryEnabled()` is `MEMORY_ENABLED === "true" && MEMORY_ADR_ACCEPTED`.
Both must be true. The env var alone can never enable memory (NN#1) — the const is a build-time change that
goes through code review. Until then the entire subsystem is inert: no fact is written, none is recalled,
and production behaviour is byte-identical to before the program.

**How to read this list.** Every item is either **MET** (with the evidence), **OPEN** (with what is
missing), or **ACCEPT** (a residual risk that must be consciously signed off rather than fixed). An item
being "in a PR" is *not* met — merged and verified is met.

What remains genuinely unowned is retiring the guest consent ROW itself. **UPDATE (B12, this branch) — PARTIALLY OWNED, not fully closed:** `POST /consent` now retires (deletes) the guest consent row as part of establishing the B12 link, but **ONLY when the account had NO consent record of its own yet at that moment** — deliberately conditional, not unconditional: retiring it unconditionally regressed this row's own `consent-restrictive-merge.test.ts` "BLOCK-1(a)/(b)" and "C7 (restated)" tests (both depend on a stale guest `"out"` continuing to exist and re-durabilize via N2's write-through for the case where the account already has its own record — typically because N2 itself already wrote one). So: for a shopper whose FIRST verified `/consent`+anonId call establishes the link before the account has any consent record of its own, the guest row is retired and this residual is closed for them going forward. For a shopper whose account already has a consent record by the time a link is first established (the scenario BLOCK-1(a)/(b)/C7-restated exercise), the guest row is left in place and this residual is UNCHANGED. |
| C8 | **NEW (PR #152 round 3, N3) — cross-subject consent oracle / denial primitive.** `/chat`'s restrictive-merge lookup (`server.ts`, feeding `mergeAccountConsent`) does a `lookupConsent` against a **caller-supplied** `anonId` (any signed-in shopper's own turn, as long as they attach a well-formed `anonId`) and lets that stranger's row govern the caller's OWN write this turn. A caller who wants to learn a target's `memoryOrdinary` tier can attach the target's `anonId` and observe whether their own write went through: refused ⇒ the target's row says `"out"`; succeeded ⇒ it does not. This is a 1-bit read of another subject's consent state plus a memory-denial primitive, newly reachable from an AUTHENTICATED turn rather than the anonymous C1 bearer-capability path. | Blast radius is bounded — holding a 128-bit `anonId` already grants the larger C1 read (recall queries + serves the target's own fact text), so this adds a narrower, indirect 1-bit signal on top of an already-larger exposure, not a new class of access; the standard per-IP/per-tenant rate limits apply. **An earlier draft additionally claimed N2's write-through narrows this to "one usable probe per attacker account" — that is FALSE and has been struck** (proven by execution in security review: probes against targets that are NOT `"out"` never burn the account, and a positive hit is undone by a single `POST /consent` with the caller's own shopper token, so the oracle is repeatable at ~2 requests per positive). |
| C9 | **NEW (PR #152 round 3, N4) — the cross-subject consent read (C8) is unaudited.** When subject X's write is refused because subject Y's row said `"out"`, nothing in the immutable log attributes the decision to a second subject's record: `lookupConsent` writes no audit of its own, and `service.ts`'s `remember()` writes NO audit at all for a plain consent-gate refusal (`write.refused` is emitted only for the SEPARATE encryption-fail-closed case — `chat-memory-remember.test.ts` locks this in deliberately). An operator cannot reconstruct that a second subject's consent record drove a given refusal. **Not closed this round** — N2's write-through DOES add a NEW, adjacent audit trail for the specific case where the merge discovers a durable-worthy `"out"` (a `consent.record` entry is written the first time), so an operator inspecting the log can see *that* the account's consent state changed, but that entry does not itself say "because a guest row was consulted" nor identify which guest row. Extending `service.ts`'s own `write.*`/`write.refused` audits to carry a PII-free "a guest row was consulted, merged tiers X/Y" marker (per N4's own text) would need a new `MemoryCtx` field threaded through `remember()` and a change to the pre-existing, tested "consent-denial is silent" invariant (`chat-memory-remember.test.ts`) — a larger, separately-scoped change, not made here to avoid touching that locked-in behavior without its own solution-architect review. | Bounded: the decision itself is still correct and fail-safe (a stranger's row can only make the caller's own write MORE restrictive) — what is missing is reconstructability, not correctness. **Not self-limiting:** an earlier draft said this was self-limiting after N2, inheriting the C8 "one-shot" claim that has since been struck as false. |
| C10 | **NEW (PR #152 round 3) — a third party can DURABLY deny a victim's memory by poisoning their consent.** `/widget/token` mints a tenant token from a *publishable* embed key with no auth, so an attacker holding a victim's guest `anonId` can `POST /consent` recording `"out"` for that subject (this half is pre-existing C1). What round 3's write-through (N2) adds: on the victim's next signed-in `/chat` turn — while their browser still presents that `anonId` — the merge **persists `"out"` onto `acct:<victim>`**. Before N2 this was per-turn and self-healing; it is now durable against new devices, cleared storage, and the victim's own later opt-in. | Direction is privacy-CONSERVATIVE (it can only deny memory, never grant it), which is why it is accepted rather than fixed — but it is a genuine third-party-triggered durable denial and must be signed knowingly. Distinct from C7 (the shopper's own stale record) and C8 (a caller poisoning their own account).  Also note: unlike the other two memory writes on `/chat`, the write-through does NOT carry `!no_autonomous_action`, so a poisoned `"out"` can be durably persisted even on a guardrail-halted turn. Deliberate — the write is strictly restrictive, so suppressing it would only DELAY honoring an opt-out — but recorded here rather than living only in a code comment. The kill switch still overrides it (NN#4, test-locked).  Attribution caveat: a `/consent` call carrying NO shopper token still records `actor: "shopper"` / `source: "shopper"` for a subject the server verified nothing about (this bearer path), so the immutable log cannot distinguish a verified shopper's own choice from a bearer-capability write. |
| C11 | **NEW (PR #152 round 3) — consent records survive `/forget`, and one of them is now created autonomously.** `eraseSubject` (`widget-memory/src/erasure.ts`) deletes the subject's vector namespace and audits it; it never touches the `memory_consent` KV. So after a signed-in shopper's "forget everything", both their guest row and the `acct:` row written by N2's merge remain. No surface removes them, and nothing in `docs/` previously recorded this erasure-scope decision. | Retaining an `"out"` is defensible as a SUPPRESSION record (it is what keeps a withdrawal effective after erasure). Retaining an `"in"` after an erasure request is NOT obviously defensible and needs a decision. Newly acute because N2 means the `acct:` row was never created by the shopper at all. Requires a stated decision at go-live, not necessarily a code change. |
| C12 | **The consent write-through's failure is not in the immutable audit log.** If `recordConsent` throws on the `/chat` path, `server.ts` catches and emits a PII-free console signal (`tenant` + error CLASS only, matching `retention.ts`'s rule) — but NO audit entry, and unlike the retention sweep's signals it omits the hashed `subjectRef` and attempted count, so an operator sees THAT a write-through failed, not for WHICH subject. The turn itself still honors the merged `"out"` (the read-time merge already applied it), so the failure degrades to pre-N2 per-turn behavior, never to a permissive one. (An earlier draft of this row said "no audit entry, no operator signal" and contrasted it with the sweep — both wrong: the console signal exists and uses the same mechanism. Overstating a residual is still misdescribing the code.) | Safe direction, but a persistent store failure would silently mean opt-outs never become durable, identifiable only at the tenant level. |
| C13 | **Two independent shopper-principal derivations.** `/chat` derives the verified shopper inline (`server.ts`) rather than calling `verifiedShopperIdFor`, which `/consent` and `/forget` use. Both apply identical gates today (feature flag, verified merchant principal, `kind === "shopper"` AND the explicit `verified` flag, cross-shop tenant check) and reviewers confirmed equivalence — but it is two implementations of one security decision. | Narrow drift risk, documented in `server.ts` but previously absent from §C, so a signer accepting the residual list never saw it.
